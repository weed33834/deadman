# deadman To B 产品设计文档

> 版本：v1.0（草稿）
> 状态：设计评审
> 关联：[技术设计文档](./B2B-TECH-DESIGN.md)
> 范围：从「C 端生前准备 + 身后办理 AI 引导员」转向「面向处理身后事的机构 / 企业的多租户平台」

---

## 1. 背景与目标

### 1.1 现状问题

- 当前产品是 C 端单机工具：个人注册、个人拥有数据、依赖文件存储、无机构概念。
- 核心资产（34 省身后事知识库、机构名录、热线、民俗规则引擎、材料包生成）无法被企业规模化使用。
- 商业模式为空：C 端免费工具无法支撑运营成本，且「死亡」场景的 C 端付费意愿低、获客贵。

### 1.2 转型目标

把平台的核心资产打包成 **企业（机构）可租用、可私有化部署、可管理自身客户与团队的 SaaS**：

1. 机构 = 租户，独立管理成员、客户、案件与数据。
2. 机构员工通过「工作台」办案，客户通过「对话 / 自助」被服务。
3. 平台持续更新政策知识库，机构订阅更新服务，形成续费点。

### 1.3 范围决策

| 决策项 | 结论 | 理由 |
|---|---|---|
| 目标客户 | 全行业（殡葬 / 保险 / 银行 / 公证 / 律所 / 政务代办），先做样板行业 | 避免代码分叉，行业差异走模板 |
| 交付模式 | 多租户架构；SaaS = 多租户实例，私有化 = 单租户实例 | 一套代码两条交付线 |
| 管理用户 | 机构员工（RBAC）+ 客户档案（机构数据）双轨 | 这是 To B 的核心卖点 |

## 2. 目标客户与样板行业

### 2.1 目标画像（第一版锁定）

| 行业 | 使用场景 | 付费意愿 | 优先级 |
|---|---|---|---|
| 殡葬一条龙服务商 / 殡仪馆 | 客户治丧全程管理、政策查询、材料包 | 高（客单高） | P0 样板 |
| 保险公司（寿险 / 理赔） | 理赔材料清单、遗产衔接、客户提醒 | 高 | P1 |
| 银行 / 公证处 / 律所 | 遗产继承、公证流程、合规留痕 | 中高 | P1 |
| 政务 / 社保代办 | 丧葬费、社保、医保代办流程 | 中 | P2 |

> 第一版只做 **殡葬服务商** 一个样板行业（M1–M5 全部用它验证），
> 其余行业通过「行业模板」（自定义字段 + 自定义流程 + 自定义知识分类）在稳定后复制。

### 2.2 行业差异如何表达（模板化，不写分支代码）

```text
行业模板 = 字段模板 + 流程模板 + 知识库分类 + 材料包模板 + 术语表
殡葬模板：字段[治丧日期/殡仪馆/墓地] 流程[接运→守灵→火化→下葬] 
保险模板：字段[保单号/受益人] 流程[报案→材料→理赔]
```

模板存储为结构化 JSON（组织创建时选定，运行期可增补字段），核心代码不感知行业。

## 3. 用户角色

| 角色 | 层级 | 说明 | 典型操作 |
|---|---|---|---|
| platform_admin | 平台 | 平台方运营，管理所有机构、套餐、封禁 | 建机构、查用量、开许可证 |
| org_admin | 机构 | 机构管理员，管理成员 / 计费 / 全部客户 | 邀请成员、分配角色、看审计 |
| case_manager | 机构 | 办理员，处理具体案件 | 建客户、办案、生成材料包 |
| consultant | 机构 | 顾问，查看客户并参与对话 | 查客户、写报告（只读为主） |
| viewer | 机构 | 只读（如管理层 / 合规） | 查看仪表盘与报表 |
| 客户 / 家属 | 客户侧 | 被服务对象，使用对话自助 | 问政策、提交材料、看进度 |

> 客户本人不登录机构工作台。客户通过机构提供的链接进入「客户门户」（简化版对话 + 材料提交），数据归属机构。

## 4. 核心用户旅程

### 4.1 机构入驻（1 天）

```
平台注册 → 创建机构（选行业模板/套餐） → 成为 org_admin
→ 邀请成员（邮件链接，token 24h 有效） → 成员接受加入
→ 成员登录进入工作台
```

### 4.2 客户办案（核心旅程）

```
工作台新建客户档案（本人+关系人+省份+阶段）
→ 系统自动匹配该省政策/机构/热线（平台公共知识库）
→ 按行业模板创建案件（分配办理员、设置阶段状态机）
→ 办理员推进案件：政策引用 / 生成材料包 / 发起通知信函
→ 客户经客户门户提交补充材料 → 案件归档
→ 全程留痕（谁/何时/做了什么），可导出审计报告
```

### 4.3 续费 / 增购

```
订阅到期前 30/7/1 天提醒 org_admin
→ 知识更新订阅（政策库季度更新包）→ 升级套餐扩用户数/存储
→ 到期未续：机构账号冻结（只读），数据保留 N 天可导出
```

## 6. 工作台信息架构（机构视角）

```
机构工作台（登录后默认页）
├── 仪表盘         客户总数 / 进行中案件 / 我的待办 / 到期提醒 / 团队负载
├── 客户           列表 → 详情（档案 / 案件 / 材料包 / 对话记录 / 审计）
├── 案件           列表 → 详情（状态机 / 任务 / 分配 / 时间线）
├── 知识库         平台政策库（只读）/ 机构自建（民俗模板 / SOP / 价格）
├── 成员           成员列表 / 邀请 / 角色管理 / 登录记录
├── 审计           操作日志 / 导出
└── 设置           机构资料 / 行业模板 / 套餐与配额 / 数据导出 / 品牌（P2）
```

导航结构独立于现有 C 端界面（`index.html` / `mobile.html`），复用现有 `admin.html` 的技术栈做成「机构控制台」页面。

## 7. 商业模式

### 7.1 定价模型

| 形态 | 计费 | 说明 |
|---|---|---|
| SaaS 订阅 | 按机构 × 员工数 × 月费 | 含平台公共知识库使用权 |
| 私有化授权 | 一次性授权 + 年度维护费 | 授权码控制实例数/用户数/模块开关 |
| 知识更新订阅 | 季度/年度 | **核心续费点**：政策库持续更新 + 法规合规报告 |
| 增值模块 | 按模块 | 客户门户 / 开放 API / 白标 |

### 7.2 授权码（License）设计要点

```
license = { instance_id, org_limit, user_limit, features:[...], expires_at } 
签名 = HMAC-SHA256(platform_secret, payload)
私有化实例启动时校验，无授权码进入 30 天试用模式（日志警告）
```

### 7.3 成本结构提示

- LLM 用量按租户配额隔离（现有 `billing/usage_tracker` 已支持）。
- 公共知识库维护成本是平台固定成本，由订阅摊销，**这是与自建机构拉开差距的地方**。

## 8. 数据与合规

### 8.1 隐私与法律

- 客户档案含身份证/健康/遗嘱等敏感信息，严格遵守 PIPL。
- 平台提供机构《数据处理协议》（DPA），明确平台与机构的数据责任。
- 客户数据的访问、删除、导出权归属机构；平台方无客户数据访问权（除故障排查，需审计）。
- 政策输出必须带「来源 + 核实日期 + 以官方为准 + 转人工」四要素（技术文档 §7 强制实施）。

### 8.2 数据保留

- 机构删除客户 = 软删除 + 30 天恢复期 + 永久清除。
- 机构到期未续费：冻结（只读）→ 保留 90 天 → 提供导出后清除。
- 审计日志按租户独立保留（默认 2 年）。

## 9. 成功指标

| 类型 | 指标 |
|---|---|
| 北极星 | 机构每周新增「进行中案件」数 |
| 激活 | 机构入驻→首个客户档案创建时间（目标 < 1 天）|
| 价值 | 每案件平均使用材料包次数、政策引用次数 |
| 留存 | 机构月度续费率、知识订阅续费率 |
| 效率 | 办理员人均结案数、平均案件周期 |
| 信任 | 审计导出使用次数、越权拦截告警数（应为 0）|

## 10. 明确不做的事（边界）

1. 不做 C 端公域产品（个人注册入口保留仅作为机构邀请成员的一环）。
2. 不做跨机构数据交换 / 客户转让市场（PIPL 风险）。
3. 不做按行业分叉代码（只做模板）。
4. 不把「通用智能体平台」当作对外卖点（MCP/A2A/编排层仅内部实现细节）。
5. 不做实时聊天 IM 系统（客户沟通走现有对话 + 材料提交即可，P2 再评估 Webhook）。

## 11. 里程碑（产品侧验收口径）

| 里程碑 | 产品验收标准 |
|---|---|
| M1 组织地基 | 一个机构能从注册到邀请 3 名成员并分配角色，数据互不可见 |
| M2 数据隔离 | 两个机构同时办案，交叉访问全部 403，审计可追溯 |
| M3 客户+案件 | 完成「建客户→办案→生成材料包→归档」全流程 |
| M4 工作台 | 机构员工 30 分钟内不培训学会办案；仪表盘数据实时 |
| M5 交付 | 私有化镜像一键启动 + 授权码生效 + 数据导出可用 |
| M6 清理 | 对外只有一个入口、一份品牌、一套叙事 |

> 详细任务拆解见技术设计文档 §11。
